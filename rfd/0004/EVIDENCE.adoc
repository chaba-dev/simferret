= RFD 4 Evidence

== Phase 0 pinned time model

=== Scale selection

The selection rule is the one the RFD records: a fixed value that boots and
completes every validation run within the configured deadline on every host in
the supported matrix, justified against its neighbors and recorded with the
reason.

The validation deadline is the probe's per-run QEMU deadline, 180 s
(`SIMFERRET_QEMU_TIMEOUT`), and every configuration below was measured with the
probe's default of five requested runs. A run that times out, exits nonzero, or
reports a malformed measurement is recorded and excluded from the comparison; a
configuration is rejected when no run completes, when the control checksum
varies, or when the spin count and state disagree.

The checked-in command is:

[source,shell]
----
SIMFERRET_ICOUNT_OPTIONS=<shift=N,sleep=off> \
SIMFERRET_TIME_MODEL_OUTPUT=<directory> \
.agents/dev ./scripts/time-model-probe.sh
----

Every run used `sleep=off`, the pinned QEMU 11.1.0, the guest kernel 6.18.49,
`-machine pc-i440fx-9.2,accel=tcg`, `-cpu qemu64`, one vCPU, `-rtc
base=2000-01-01T00:00:00,clock=vm`, and one initramfs
(`sha256 24d0dfffc169a4275657c61281097882447fd565ecff87eb619cc587a57e1b4c`), on

Every value is exact across its five runs: all twenty-five runs completed, no
time measurement varied, and the control checksum was identical in all of them.
The spin count is the one measurement that differs between models, 128 chunks at
`shift=2` against 64 at `shift=3` and coarser, which is the polling quantization
the probe documents rather than a reproducibility difference; the spin state
agreed with the count in every run. The `shift=4` and `shift=7` rows reproduce
link:../../poc/time-model/EVIDENCE.adoc[the pre-RFD measurement] exactly
(21.951 ms, 117.78 ms, 330,255 B; 20.948 ms, 207.06 ms, 3,303,901 B), so the
model is stable across sessions rather than only within one experiment.

The chosen value is `shift=4,sleep=off`:

* Correctness does not discriminate. `shift=2`, `shift=3`, `shift=4`, `shift=5`,
  and `shift=7` all reproduce exactly, so the validated window is flat in
  reproducibility and the choice is a semantic one about the artificial
  performance model.
* The fine direction has no measured failure mode and is cheaper on every
  measured axis: the replay log falls from 3,303,901 B at `shift=7` to 85,633 B
  at `shift=2`, the run wall time from 14.07 s to 6.32 s, and the fixed
  computation from 2,262.144 ms to 42.746 ms. A rule of "the finest value
  validated so far" would therefore keep moving as finer values are measured,
  which is a poor basis for a versioned constant.
* `shift=4` is the value the pre-RFD measurement analyzed and the published RFD
  cites: it completes no slower than `auto` (6.70–6.76 s here against 6.77–6.80 s
  under `auto`) and writes a replay log an order of magnitude smaller than
  `shift=7`. Its immediate neighbors on both sides (`shift=3` and `shift=5`) are
  validated here, so the choice is not at the edge of the measured window and its
  justification is complete against both directions.
* The coarse direction is the one with a measured failure mode. The exploratory
  `shift=10` run produced no guest output within the deadline and a 117 MB
  replay log, and the fixed computation grows faster than the exchange rate
  between `shift=5` and `shift=7` (387.858 ms to 2,262.144 ms, 5.8x for two
  steps), so the choice should sit inside the window rather than at its coarse
  edge.
* Observed overshoot is recorded rather than optimized, as the RFD requires, and
  it is not monotonic in the scale. The 20 ms sleep overshoots by 0.076 ms at
  `shift=2`, 0.103 ms at `shift=3`, 1.951 ms at `shift=4`, 0.284 ms at `shift=5`,
  and 0.948 ms at `shift=7`; the 100 × 1 ms loop totals 111.577 ms, 115.003 ms,
  117.778 ms, 124.969 ms, and 207.060 ms respectively.

`shift=3` and `shift=2` are equally reproducible and cheaper, and either is
available if the artifact size or the virtual-time inflation of CPU-bound work
later matters more than stability of the constant; changing the value afterwards
is a versioned change, because the model is part of VM identity and runs recorded
under different models are not comparable.

This section measures the reference host only, which is half of the rule. The
supported matrix adds GitHub-hosted `ubuntu-latest` x86-64 Linux, where the
Phase 0 continuous-integration gate requires every requested run to complete and
the verdict to be `reproducible`, and where a host that cannot complete under the
pinned model must fail as an unsupported execution rather than fall back to
another model. Pinning a different scale later is a versioned change, because
the model is part of VM identity and runs recorded under different models are not
comparable.

Raw per-run serial output, replay logs, and durations remain in the untracked
`.poc/rfd4-phase0/` directory.

=== Validation on the reference host

The validation deadline is the probe's per-run QEMU deadline, 180 s
(`SIMFERRET_QEMU_TIMEOUT`), and the sample is the RFD's minimum of five complete
runs. `scripts/time-model-gate.sh` fixes both rather than inheriting them from
the caller: a different deadline, a smaller sample, or a sample larger than the
probe's own bound is a configuration error before any run starts, and the gate
fails a host unless every requested run completed, the verdict is an explicit
`reproducible`, and the guest measurements equal the checked-in reference values
exactly. Failures are classified rather than merged into one status: a bad
record, an unsupported platform, or a probe that rejects its arguments is a
configuration error; a host that did not complete the runs is an unsupported
execution and no fallback model is attempted; and a completed experiment that
disagrees with the reference record, or that is invalid on its own control
checks, is a validation failure. The probe's own outcomes are mapped rather than
merged, and an exit the probe does not document is not read as a statement about
the host. Each invocation creates its own directory under the output root before
anything is validated, with its result file, the probe's output, and the probe's
run directory, so a configuration error is recorded where it happened and a
failed rerun cannot leave an earlier success standing.

The checked-in command is:

=== Cross-host equality

Requiring zero variation within a host is not the RFD's rule; the rule is that
the guest measurements are equal across the supported hosts for identical
artifacts and the same model. The gate therefore compares each host against the
reference host's checked-in values instead of only against itself, and it checks
the artifacts that make the comparison meaningful: the SHA-256 of the QEMU
executable, of the guest kernel, and of the initramfs the probe builds. A host
whose guest measurements differ fails the gate rather than passing with a
warning.

The reference host is the half measured here. The `ubuntu-latest` half is
measured by the `qemu-replay` job in `.github/workflows/ci.yml`, which runs
`scripts/time-model-gate-test.sh` and then the gate itself. Its first green run
(GitHub-hosted `ubuntu-latest`, QEMU 11.1.0, the same kernel and initramfs
digests) reproduced every value exactly: 5 of 5 requested runs completed, the
verdict was `reproducible`, the four time measurements and the control checksum
were identical to the reference host's, and every replay log was 330,255 bytes.
The two hosts therefore agree on the measurements rather than each being only
internally stable, which is the rule this section exists to enforce. The run is
retained at
https://github.com/chaba-dev/simferret/actions/runs/35672759147/job/106572696097.

=== Record mode cannot use the pinned model

The gate validates the model for a guest that never waits for host input, which
is what the probe does. The product's guests do wait: a recording is driven by
control commands written to the guest's serial port. Measuring that case
separates the model's reproducibility from its usability, and it fails.

`scripts/time-model-input-probe.sh` boots `poc/time-model/input-probe.c`, waits
for the guest's `READY`, writes one line, and reports whether the guest received
it. The guest polls with a 100 ms timeout rather than blocking, so it also
measures delivery while virtual time keeps advancing, and it has no poll limit:
it polls until the line arrives or the probe stops the emulator.

The order of operations is the measurement, and QEMU's monitor is what makes it
causal rather than timing-dependent. The guest polls until the probe stops the
emulator, so a bounded guest window cannot close before the write. The probe then
stops the guest with an acknowledged monitor command (it waits for QEMU's reply,
so a request QEMU has not acted on is not mistaken for a stopped guest), drains
the output the guest produced before it stopped, writes the line, and resumes the
guest with a second acknowledged command. A stopped guest cannot poll and cannot
produce output, so the polling it does after the resume is polling after the
write, and no report read after the resume can be one the guest produced earlier;
without that ordering the result would rest on how the host happened to be
scheduled, which is exactly what a reproducibility measurement must not do.
After the wait the probe stops the emulator and reads its output to its end
before closing the pipe, so a delivery report emitted while the emulator is being
stopped is classified rather than lost. Only an output that ended in one piece
supports a non-delivery claim: an end that never arrives, a report cut off
mid-line, or the emulator's own deadline expiring all leave the experiment
inconclusive, because in those cases the probe cannot say that nothing else was
coming.

`input=not-delivered` therefore means: the guest reported `READY`, produced a
poll report after the resumed write, the write succeeded, the guest had not
stopped polling for longer than the stall bound, the emulator was still running
when the wait expired and was stopped by the probe, and its output then ended in
one piece, with no delivery report seen before or during shutdown. The stall
bound is a liveness heuristic rather than a proof — a host stalled while
consuming output cannot tell old progress from new — but the ordering does not
rest on it, because the acknowledged stop and resume do. Receiving the line is
reported whatever else the experiment did, and a guest that never reported
`READY`, a host that could not write the line, a guest that produced no poll
report after the write, an emulator that exited on its own, an output that did
not end or ended mid-report, or a deadline that expired is inconclusive, which
satisfies no assertion. All four measurements used the pinned QEMU, the pinned
kernel, and the same probe build:

| `-icount` options | Replay | Host input delivered

| `shift=4,sleep=off` (pinned)
| `rr=record`
| *no*, the guest polled for the 84 s after boot, reporting 26,740 polls, and never received the line

| `shift=4,sleep=off` (pinned)
| none
| yes

| `shift=4`
| `rr=record`
| yes

| `shift=auto` (what the product launches today)
| `rr=record`
| yes
|===

The command that reproduces each row is:

[source,shell]
----
.agents/dev ./scripts/time-model-input-probe.sh                # pinned model, records
.agents/dev ./scripts/time-model-input-probe.sh --live         # pinned model, no record
.agents/dev ./scripts/time-model-input-probe.sh shift=4        # sleep=on control
.agents/dev ./scripts/time-model-input-probe.sh shift=auto     # the product's current model
----

Continuous integration asserts the known result rather than leaving it to be
re-checked by hand: the `qemu-replay` job runs
`scripts/time-model-input-probe.sh --expect not-delivered`, so a QEMU change
that starts delivering input under the pinned model fails the job with the
reading that the pin may be unblocked. The same job runs the guest's own
regression tests (`scripts/time-model-input-probe-test.sh`), which drive the real
polling loop through stubs: a line that arrives after more than the polls the
guest used to stop after is still reported as received, and the guest never
reports giving up, so restoring either fails there rather than passing.

The cause is in QEMU rather than in the host. With record/replay enabled, live
character input is not delivered when it is read: QEMU queues it as a
`REPLAY_ASYNC_EVENT_CHAR_READ` and delivers it only when the replay event queue is
flushed, which happens in `replay_async_events()` from
`icount_account_warp_timer()`. That function returns immediately when
`icount_sleep` is false, which is what `sleep=off` sets. Under the pinned model
the guest therefore never receives the bytes, whether it blocks on a read, polls
with a timer, or busy-polls, and whether the host writes them before or after
boot.

The limitation is not specific to record mode. In QEMU 11.1.0
`replay_async_events()` has exactly one caller, that function, and it is the
single site that saves queued events in record mode and injects recorded ones in
replay mode through `replay_read_events()`; `sleep=off` therefore skips
asynchronous input in both directions. A guest that needs no host input still
records and replays, which is why the time-model probe is unaffected, but a
recording under this model cannot be made and an existing recording's
asynchronous input would not be injected either. The spike below shows a patch
restoring that single processing site for both modes.

The same limitation reaches the product and the earlier increments' spikes:

* `scripts/phase4-acceptance.sh` records with the product and fails with
  `simferret: timed out writing command to guest` after the first command, with
  `traffic.requests_attempted: 0` in the failure diagnostics.
* `scripts/qemu-network-replay-smoke.sh` fails because the guest's TFTP fetch
  times out: the SLIRP response is also a replay asynchronous event, so it is
  queued rather than delivered.
* `scripts/qemu-replay-smoke.sh`, which needs no host input, passes under the
  same model, so the failures are specific to asynchronous input rather than to
  record and replay as a mechanism.

What this blocks: Phase 0's requirement that the product's record and replay
launch paths pass the pinned model, and its requirement that a run recorded under
the pinned model replays twice with matching events, assertions, and outcome
digest. A recording cannot be made under the pinned model, so the second
requirement cannot be satisfied by any implementation that does not first change
how input reaches the guest. Until that is decided, the product's launch paths
keep launching the model they can complete under, which
`crates/simferret/src/vm.rs` names `TIME_MODEL` and documents there.

The decision this leaves to the RFD is not a scale choice. It is one of: keep a
fixed scale and drop `sleep=off`, which reintroduces the residual host-coupled
variation the scale-selection section measured; fix QEMU's no-sleep replay path
so queued asynchronous events are flushed at a deterministic point; or deliver
input to the guest by a mechanism that does not depend on the replay event queue,
which is the deterministic-ingress work this RFD already separates from the
model.

==== What this measurement does not establish

The measurement is the strongest ordering the emulator exposes, and it is worth
being explicit about what it rests on, because the blocker claim is only as good
as the ordering it is measured under.

* The acknowledged stop and resume are asserted in the harness, not fixtured for
  the delayed case. `scripts/time-model-gate-test.sh` drives the probe against a
  QMP-speaking double and asserts that the monitor log contains `stop` and `cont`
  around the write, and the probe's own code waits for QEMU's reply before it
  drains and writes, so a request QEMU has not acted on cannot be mistaken for a
  stopped guest. A fixture for the case where the pause takes effect only after
  the request was written was dropped: its timing could not reliably distinguish
  the acknowledgement from the delay, so the delayed-pause behaviour is reasoned
  about rather than measured.
* That nothing remains buffered in the guest or the output path when the write is
  submitted is a source-level argument rather than a monitor-level one. QEMU's
  stdio chardev writes guest output through `io_channel_send` with no user-space
  buffer, so a drained pipe is the boundary between what the guest produced before
  the write and what it produces after the resume; QEMU exposes no "output
  flushed" acknowledgement at the monitor, so this part cannot be asserted through
  the channel that orders the write. The stall bound in the probe is a liveness
  heuristic for the same reason: a host stalled while consuming output cannot tell
  old progress from new.
* The causal claim does not depend on the probe's instrumentation alone. The
  spike below changes one early return in QEMU's `icount_account_warp_timer()` and
  delivery appears under the same model with the same probe, which is independent
  confirmation that the flush ordering is the cause of the non-delivery rather
  than an artifact of how the probe accounts for it.

=== Feasibility spike: a patched QEMU that flushes the queue

The blocker above is one early return. `poc/time-model/qemu-nosleep-replay-flush.patch`
moves the flush before it, and `poc/time-model/qemu-nosleep-replay-spike.nix`
builds the pinned QEMU with that patch applied. Neither file is wired into
`flake.nix` or into any build the repository performs; they answer whether a
minimal fix is possible, and carrying a patched QEMU remains a project decision.

[source,diff]
----
 void icount_account_warp_timer(void)
 {
-    if (!icount_sleep) {
-        return;
-    }
-
     /*
      * Nothing to do if the VM is stopped: QEMU_CLOCK_VIRTUAL timers
      * do not fire, so computing the deadline does not make sense.
      */
     if (!runstate_is_running()) {
         return;
     }
 
+    /*
+     * Flush queued replay events before the sleep check. External input is
+     * queued as a replay asynchronous event and delivered by this flush, so
+     * returning first would leave a guest that waits for host input without
+     * it in both record and replay mode.
+     */
     replay_async_events();
 
+    if (!icount_sleep) {
+        return;
+    }
+
     /* warp clock deterministically in record/replay mode */
     if (!replay_checkpoint(CHECKPOINT_CLOCK_WARP_ACCOUNT)) {
         return;
     }
----

The build is:

[source,shell]
----
rev=$(jq -r '.nodes.nixpkgs.locked.rev' flake.lock)
nix build --impure --no-link --print-out-paths --expr "
  let pkgs = import (builtins.fetchTarball
        \"https://github.com/NixOS/nixpkgs/archive/$rev.tar.gz\") {};
  in import ./poc/time-model/qemu-nosleep-replay-spike.nix { inherit pkgs; }"
----

It produced `/nix/store/6a4jza3ydplb1k9l4kbk9gcsqy2iaka8-qemu-11.1.0`, whose
`qemu-system-x86_64` reports the same `QEMU emulator version 11.1.0` and hashes
to `f9c26bcdcd50ecbbccd923840bbcfaede6fddc675764cd99c93e12e97779faa8`. Every
measurement below used that binary through `QEMU_SYSTEM_X86_64`, and the

The gate row is the behaviour the QEMU digest exists for: the patched binary
reports the same version string, and only the digest distinguishes it.

The acceptance run is the two-replay confirmation this increment cannot make
under the pinned model otherwise. Its normalized artifacts are byte-identical to
the artifacts recorded under the product's current model in the same session:
`events.jsonl` SHA-256 `e95693c7adee291b3f40ce6457189a6832402021826428c510c2f7f0bb55bd4d`,
`assertions.json` SHA-256
`d95cf483f182e37ff31687b80599dd37d2a877336eb966cb42c754faed4ea83f`, and
`semantic_outcome_sha256` `be5ec6342d82234bc8d28ad538cf1dca34d38e42106fd9e12aec3e918fc0c927`.
Only the replay log differs, 3,539,432 bytes under the pinned model against
6,384,125 bytes under the current model, which is a measurement rather than
identity, as RFD 2 already scopes it.

Replay semantics. The flush is not moved past a checkpoint; the no-sleep path
simply stops skipping it. In record mode `replay_async_events()` writes the
queued events at the current instruction count and then runs them, and
`replay_checkpoint(CHECKPOINT_CLOCK_WARP_ACCOUNT)` still follows in every path
that reaches it, in the same order as before. With `sleep=on` nothing changes:
the running-state check, the flush, and the checkpoint happen in the same
sequence, and a stopped VM still returns before the flush in both modes. With
`sleep=off` the checkpoint and the clock warp are still skipped, exactly as they
were, so the change adds the flush without touching checkpoint ordering. The
events therefore keep their instruction-position semantics, which is what the
two-replay comparison above measures.

What an upstream submission would argue: `-icount sleep=off` is documented as
giving deterministic execution times from the guest's point of view, and
record/replay is documented as recording and replaying serial, network, and
input-device input. Those two documented behaviours do not compose today,
because the only flush site for asynchronous events sits behind the sleep check.
Moving the flush ahead of that check keeps checkpoint ordering, changes nothing
for `sleep=on`, and makes `sleep=off` usable for guests that receive input. The
counter-argument to expect is that a change here should come with a record/replay
test covering input under `sleep=off`; the measurements above are the basis for
one.

Recommendation: the fix looks minimal, effective, and upstreamable, and it does
not perturb the model's measurements. Whether to carry a patched QEMU until an
upstream release includes it is the project's decision; this increment does not
do that, and the product keeps the model it can complete under.

=== Re-validation trigger

The model, the reference values, and the input result are valid only for the
pinned QEMU and guest kernel they were measured with. Re-validate when any of
these changes:

* the pinned QEMU or guest kernel, in practice a `flake.lock` update that moves
  `pkgs.qemu` or `pkgs.linuxPackages.kernel`;
* the model recorded in `poc/time-model/reference-host-values.txt`;
* `poc/time-model/probe.c`, which changes the guest and therefore the initramfs
  digest the gate checks; or
* `poc/time-model/input-probe.c`, which changes the input probe's own guest, so
  the input result below must be re-measured; the gate does not check that
  initramfs.

Re-validation means running `scripts/time-model-gate.sh` on every host in the
supported matrix and `scripts/time-model-input-probe.sh` for the models in the
table above, then re-recording the results here and the values in the reference
