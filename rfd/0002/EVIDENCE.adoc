= RFD 2 Evidence

== Purpose

This record starts with the pre-implementation spikes that tested whether the
network boundary proposed by RFD 2 was feasible with the QEMU, kernel, machine,
and unprivileged CI constraints committed by RFD 1. The final sections record
the integrated implementation and acceptance evidence.

== Sophie runner baseline

The `sophie` x86-64 Linux runner fetched `origin/main` at commit `e27ffb2f` and
ran the repository's pinned QEMU 11.1.0, Linux 6.18.49, machine
`pc-i440fx-9.2`, and TCG as an unprivileged user.

The RFD 1 QEMU smoke test passed in 24.97 seconds. Its internal record duration
was 5.75 seconds and its two replay durations were 8.89 and 9.43 seconds. The
5,863,403-byte replay log had SHA-256 digest
`b0c696f907f8706e8147506e9948dc7c9c19e648a798dc5a1a74d162a4186090`.
All serial outputs had SHA-256 digest
`3771b23d96c0b8635c375ecb9e3c39664890e3dc7f5eb06a3317041799f25b66`.

The complete RFD 1 acceptance demonstration also passed in 236.35 seconds. The
normal record took 54.96 seconds, its replays took 63.40 and 62.95 seconds, and
the intentional-corruption record took 53.91 seconds. Artifact tampering,
identity tampering, and intentional fixture corruption produced their expected
failures.

== RTL8139 ingress and passive replay on Sophie

A disposable spike used this replay-relevant network shape:

[source,text]
----
-device rtl8139,netdev=net0,mac=52:54:00:12:34:56
-netdev user,id=net0,restrict=on,hostfwd=udp:127.0.0.1:45555-:12345
-object filter-replay,id=net-replay,netdev=net0
-icount shift=auto,rr=<record|replay>,rrfile=<replay.bin>
----

The guest received the 23-byte payload `simferret-network-spike` from
`10.0.2.2` and emitted `NET_SPIKE_OK`. Record mode completed in 6.54 seconds.
Two replays without the host forward or sender completed in 10.87 and 11.10
seconds with byte-identical serial output.

A stronger replay replaced the recording-time user backend with an isolated
socket netdev listening on a private unused address and no peer. It completed in
11.20 seconds with the same serial output. This directly establishes that
replay requires a netdev object for structural attachment but does not require
the recording backend, host forward, sender, or peer interaction.

The 8,335,311-byte replay log had SHA-256 digest
`47df1845882b06f7020c40cf24f1a35429d804cb6eef13585c261be2d7962fa2`.
The record and all three replay serial streams had SHA-256 digest
`c96da14b312c0e61c09dbdefb550bb4a165ca914165f9201703afd467d23bc38`.
Against the focused no-network smoke run, this one-packet sample increased log
size by 1.42 times, record duration by 1.14 times, and replay duration by
approximately 1.2 times. It is not a throughput forecast.

== Outage and recovery spike in an Amp orb

A second disposable spike used QEMU 11.1.0, the same kernel and machine, an
explicit e1000 NIC, restricted user-mode networking, built-in TFTP fixture
content, and `filter-replay`. A static BusyBox guest configured the NIC and a
fixed route.

The guest fetched matching content, installed a peer-specific `prohibit` route,
observed an immediate unavailable result, removed the route, and fetched the
matching content again. It emitted all three markers:

[source,text]
----
SIMFERRET_NET_PRE_OK version=1
SIMFERRET_NET_OUTAGE_OK version=1
SIMFERRET_NET_RECOVERY_OK version=1
----

After record mode, the TFTP fixture directory was deleted. Two passive replays
still produced byte-identical serial output. Record mode took 13.27 seconds and
the replays took 34.12 and 34.02 seconds. The replay log was 20,951,688 bytes
with SHA-256 digest
`5de81a09527cebd7aabe6fb376f4aa4504dc33fa4e0c108e9e0028c61ded801a`.
All serial streams had SHA-256 digest
`59ae1229ae23afdab0e79bee1fa80ec3b83bedc8c893d9d21673f3a4bbb5a7a2`.

This proves the initial peer-specific route fault with e1000. RFD 2 still must
repeat the integrated outage scenario with its selected RTL8139 identity.

== Checked-in RTL8139 outage tuple in an Amp orb

The checked-in `scripts/qemu-network-replay-smoke.sh` closes the gap between the
two disposable spikes. It uses the RFD's selected identity and one integrated
scenario:

[source,text]
----
-machine pc-i440fx-9.2,accel=tcg
-cpu qemu64
-netdev user,id=simnet,restrict=on,tftp=<private-run-directory>
-device rtl8139,netdev=simnet,mac=52:54:00:12:34:56,bus=pci.0,addr=0x3,romfile=
-object filter-replay,id=simnet-replay,netdev=simnet,queue=all
-icount shift=auto,rr=<record|replay>,rrfile=<private-run-directory>/replay.bin
----

The reproducible initramfs contains the pinned static BusyBox and decompressed
`mii` and `8139cp` modules. The guest verifies that `8139cp` actually binds the
NIC before testing traffic. Each bounded request maps canonically to
`request-NNNNNN`; the corresponding TFTP file contains that request identifier
and `payload-NNNNNN` for guest-side comparison.

The exact checked-in command passed in this Amp orb with one request. The record
took 10.063 seconds, its two passive replays took 32.681 and 34.212 seconds, and
the intentional-corruption record took 8.700 seconds. The three successful
serial streams were byte-identical with SHA-256 digest
`33ddf17fe726d78ffe495a37f1926284cba9038dcb218ad4874778453671dbf3`.
The 866,175-byte initramfs produced a 24,399,452-byte replay log.

Before both passive replays, the script deletes every TFTP fixture file while
retaining the same restricted backend profile. Both replays still pass. The
guest also proves that a peer-specific `prohibit` route causes `sendto` to fail
with errno 13 (`EACCES`) before removing the route and refetching the fixture.
Finally, a separate record serves corrupted bytes for the first request. The
guest emits a typed `response_mismatch` property failure and does not emit the
success marker. This demonstrates that success is derived from network-returned
content rather than the guest command alone.

The accompanying fake-QEMU regression suite passes and checks the exact network
arguments, mandatory filter, disabled option ROM, passive fixture removal,
intentional corruption, serial mismatch, missing marker, infrastructure-failure
event, invalid request bounds, comma-bearing QEMU option path, retained prior
output, and reproducible initramfs across caller umasks.

=== Independent checked-in tuple on Sophie

The same guest sources, build script, pinned dependencies, and QEMU tuple passed
independent execution on the unprivileged `sophie` runner. The regression suite
completed in 4.13 seconds. The real smoke command completed in 38.68 seconds:
record took 6.598 seconds, the two passive replays took 11.029 and 10.965
seconds, and the intentional-corruption record took 6.692 seconds.

The 866,175-byte initramfs had SHA-256 digest
`57757eb8eb820d916eee3a980e321c74bec345654f70aa5c71835d6a25f57f33`.
The 7,754,388-byte replay log had SHA-256 digest
`28ae9af6f3a0b237ee21bfee6b543638b819f84f3afa6356c7bdd3d68932d8e7`.
Record and both replay serial streams were byte-identical and matched the Amp
orb's semantic serial digest,
`33ddf17fe726d78ffe495a37f1926284cba9038dcb218ad4874778453671dbf3`.
The corrupt run emitted the typed `response_mismatch` marker and no success
marker. All QEMU diagnostic logs were empty.

The different hosts produced materially different durations and replay-log
sizes despite matching semantic output. Replay-log byte identity across separate
recordings is therefore not a supported invariant. The transfer archive was
applied over `origin/main`, so its RFD index check failed because the archive
contained only the later robustness commit and not RFD 2's earlier index entry.
The complete RFD 2 branch contains that entry and passes the same check. This was
a validation-transfer issue, not a QEMU or repository-branch failure.

=== GitHub-hosted x86-64 Linux

The checked-in regression and real network smoke commands passed in the
`QEMU record/replay` job on GitHub-hosted Ubuntu. The complete job passed in 6
minutes 38 seconds without elevated privileges. The network record took 5.733
seconds, its passive replays took 9.008 and 8.781 seconds, and the intentional
corruption record took 5.986 seconds.

The initramfs size and digest matched `sophie`. The 3,502,215-byte replay log had
SHA-256 digest
`b5aa21826f7b9c71d85aade288611aa8c514f78b8757444d906d6d30367ce38b`.
Record and both replay serial streams again had the cross-host semantic digest
`33ddf17fe726d78ffe495a37f1926284cba9038dcb218ad4874778453671dbf3`.
The corrupt serial stream had the expected digest
`f1a0bd0af1b41a564493105a4bb213b6d1469c8dba33e36dcb74a49192dc20bb`.

The Amp orb, independent `sophie` runner, and GitHub-hosted runner therefore all
validate the selected tuple. This completes the Phase 0 feasibility gate while
leaving controller integration, typed production identities, and full RFD 2
acceptance to subsequent phases.

== Negative results and constraints

Omitting `filter-replay` allowed recording and ingress but caused replay to hang
until its 15-second watchdog expired. Referring the filter to a nonexistent
netdev, or omitting the netdev object, failed immediately because the filter
requires a backend identifier.

Changing the MAC address during replay produced partial divergence and then a
15-second timeout. Reusing the recording-time host forward while its port was
occupied failed QEMU startup. In the orb spike, omitting the filter or changing
the MAC similarly hung until a 20-second watchdog expired. QEMU therefore cannot
provide the required actionable compatibility validation; SimFerret must reject
these differences before launch.

Using a TCP `guestfwd` endpoint caused QEMU to connect to its peer during backend
initialization, including before replay could disable packet interaction. The
recording peer could not simply be absent. The disposable socket replay proved
that changing backend types can work, but a listening socket cannot guarantee
isolation from other local processes. The selected profile instead retains the
restricted built-in TFTP backend and removes its fixture content before replay.

The pinned kernel builds RTL8139, e1000, and virtio-net drivers as modules. The
RTL8139 spike required `mii`, `8139cp`, and `8139too`. Its minimal loader could
not pass compressed `.ko.xz` files directly to `finit_module`; the initramfs
decompressed them first.

Netfilter core is built in, while nftables, iptables, and netem functionality is
provided as modules. Their module dependency closures exist, but the current
guest does not contain them or a pinned `nft`, `iptables`, or `tc` executable.
A peer-specific route through pinned static BusyBox is proven and smaller for
the first outage. Rich packet faults remain unproven.

All successful network spikes ran as uid 1000 with QEMU TCG and user-mode
networking. They required no root access, TAP, bridge, KVM, or uncontrolled
Internet traffic.

== Phase 1 — Network identity and VM adapter

The VM adapter now represents the selected NIC, fixed MAC and PCI attachment,
restricted backend, mandatory replay filter, addressing, route, immutable TFTP
fixture, and peer-specific prohibit-route fault as typed semantic identity. It
constructs the complete network argument sequence and rejects changed or unsafe
profiles before QEMU starts. Replay incompatibility reports identify the first
differing field and include its expected and actual values.

Record fixture identity is derived from a bounded canonical encoding of sorted
filenames and bytes rather than accepted from the caller. The adapter traverses
the source without following directory or file symlinks, rejects special files,
and copies the verified bytes into a private runtime snapshot. QEMU receives
only that adapter-owned snapshot. Replay refuses live fixture input and creates
a fresh empty private directory with the same semantic endpoint type. Runtime
paths remain diagnostic and are excluded from the persisted identity.

Unit regressions cover exact QEMU options, unsupported backends, missing replay
filters, field-level replay diagnostics, canonical fixture identity, source and
leaf symlink rejection, special files, bounded file counts and sizes, directory
substitution, source mutation, preservation of an existing recording after
preflight failure, absolute runtime paths, passive replay emptiness, and fixture
ownership through VM launch and drop. The pre-existing no-network profile and
manifest schema remain compatible with RFD 1.

== Phase 3 — Record and passive replay integration

On September 9, 2026, the x86-64 Linux Amp runner executed
`./scripts/phase4-acceptance.sh` through the pinned development environment.
The command recorded the six-request network scenario and replayed it twice
through QEMU 11.1.0 with an empty replay fixture. Record completed in 58.47
seconds and the passive replays completed in 67.30 and 66.77 seconds. Both
replays produced the same 3,861-byte normalized event artifact, 598-byte
assertion artifact, and semantic outcome digest
`be5ec6342d82234bc8d28ad538cf1dca34d38e42106fd9e12aec3e918fc0c927`.
The 22,696,092-byte replay log had SHA-256 digest
`c79c26e825eecd9ae646fe1b3eeb2b99bb59c59c246433c60aed1006e732e069`.

The same run rejected event-artifact tampering before launch and rejected a
self-consistent VM identity change before QEMU execution. Unit regressions also
reject a missing replay filter, a fault plan whose restoration does not follow
activation, every digested network artifact change, and the first normalized
network-event divergence.

Dependency, preflight, launch, execution, publication, and replay-validation
failures now atomically retain a separate bounded bundle under the run root's
`failures/` directory. The JSON report identifies the failure stage, sanitized
validated local network configuration when available, record or passive replay
backend mode, fixture mode, observed fault transitions, and semantic
request-result counts. It reports packet counters as unavailable because the
selected QEMU user backend and replay filter expose no counter API rather than
inventing packet evidence. Error text and sanitized QEMU and guest log tails
are each limited to 64 KiB. Report-only dependency and runtime-creation bundles
do not inspect unvalidated recording logs. Real artifact- and VM-identity
preflight rejections each produced and retained a bundle during the acceptance
run.

== Phase 4 — Acceptance

The complete integration is automated by `scripts/phase4-acceptance.sh` and the
repository's `QEMU record/replay` GitHub Actions job. The September 9, 2026 main
run at commit `aa4c78a96444d27e564cb2946c02a9022cb0841e` passed all five jobs.
The unprivileged GitHub-hosted Ubuntu QEMU job completed in 8 minutes 42 seconds:

* https://github.com/chaba-dev/simferret/actions/runs/34316273634[CI run 34316273634]
* https://github.com/chaba-dev/simferret/actions/runs/34316273634/job/102353043771[QEMU record/replay job]

A final local rerun against that integrated implementation recorded in 58.08
seconds, replayed in 66.62 and 66.35 seconds, and completed the intentional
corruption run in 59.09 seconds. Its 10,089,520-byte replay log had SHA-256
digest `c64b6b74c827a2df43775e84f823b97f55d4f9def05fb1d1bf946be6333a17d1`.
Both replays matched the recorded semantic outcome digest
`be5ec6342d82234bc8d28ad538cf1dca34d38e42106fd9e12aec3e918fc0c927`.
Artifact and VM-identity rejection each retained the expected bounded failure
bundle.

The six-request seed-42 choice plan activates the outage before request index 2
and restores it before index 4. Its semantic traffic consists of six attempts,
four matching TFTP responses through the RTL8139 NIC, and two immediate
administrative rejections while the peer route is prohibited. The six canonical
fixture files materialized for recording contain 492 bytes in total and are
removed before atomic publication; this is application-level traffic evidence,
not a packet or link-byte count. QEMU exposes no packet-counter API for the
selected user backend and replay filter, so the bounded failure report marks
packet counters unavailable.

The first unavailable result follows its request attempt by one semantic event,
meeting the configured outage bound of one. The first matching response after
restoration follows the restoration confirmation by two semantic events,
meeting the configured recovery bound of two. Seed 43 changes both request
content and the fault plan: activation moves to index 1 and restoration to index
5. Its intentionally corrupted first network response fails safety and returns
CLI status 1 while the outage, restoration, and recovery assertions still pass.

Compatibility regressions alter one field in each typed network identity class:
NIC, backend, replay filter, addressing, route, fixture, and fault. Every change
is rejected before launch with the first differing field. Validation regressions
separately reject unrestricted user networking, TAP and other unsupported
backends, and a missing replay filter. Artifact tests cover every persisted
artifact, malformed choice plans, semantic inconsistencies, and normalized event
divergence.

An equivalent self-hosted run requires x86-64 Linux, Nix, and the repository's
pinned QEMU, kernel, modules, BusyBox, and Rust environment. It runs as an
ordinary unprivileged user and requires neither KVM nor TAP, a bridge, firewall
changes, or external network access. The invocation is identical:

[source,shell]
----
.agents/dev ./scripts/phase4-acceptance.sh
----

=== Limitations and observed divergence

The semantic artifacts and outcome digest are stable across passive replays,
but replay-log size and wall-clock duration vary across recordings and hosts.
They are measurements, not replay identity. The selected boundary supports one
RTL8139 NIC, one restricted user-mode backend, immutable TFTP fixtures, and one
outbound peer-specific prohibit route. It does not establish packet loss,
latency, reordering, multiple guests, or production throughput. No semantic
divergence was observed in accepted record/replay runs. Intentional content
corruption, identity changes, artifact changes, missing filters, and malformed
plans produced the expected explicit failures.

== Recommendation

QEMU's replay-filtered user network is reliable enough for the bounded model:
the same integrated scenario passed locally and on GitHub-hosted x86-64 Linux,
passive replays reproduced exact semantic artifacts, and preflight checks turned
QEMU's otherwise hanging identity failures into actionable errors. The next RFD
should add reproducible OCI workload packaging so users can apply the proven
process and network faults to their own software. Checkpoint branching should
follow once a real packaged workload supplies representative snapshot and
exploration costs.
