= RFD 3 Evidence

== Entry gate

The entry gate selects `poc/rfd3-workload/main.c` as the acceptance workload.
It is a bounded C program with no SimFerret library dependency. Its line protocol
can echo asymmetric input, create and detect invocation state under `/tmp`,
double-fork a session-leader descendant that ignores `SIGTERM` and retains
standard output, and fetch one bounded TFTP response from the existing
`10.0.2.2` RFD 2 peer. It recognizes `EACCES` from the peer-specific prohibited
route separately from malformed or unavailable responses. The `fetch` command
accepts the scenario's independently generated expected payload rather than
deriving it from the request identifier. These behaviors cover the process,
fresh-root, live-output, and network assertions required by the RFD without
putting application interpretation in the guest agent.

This selection does not claim that RFD 3 process supervision exists. Booting and
supervising the external executable remains the first Phase 0 task.

=== Representative artifact capture

The checked-in capture command is:

[source,shell]
----
.agents/dev ./scripts/rfd3-entry-gate.sh
----

It compiles the fixture as a static little-endian x86-64 Linux ELF and emits two
uncommitted inputs below one unique `.poc/rfd3-entry-gate/capture.*` directory:
the executable itself and a local OCI image layout containing that executable in
one uncompressed layer. Unique directories make concurrent captures independent

selected config, manifest, and layer blobs. The script uses canonical JSON,
USTAR metadata with zero timestamps, and a fixed entry order; it neither pulls

== Phase 0 workload and OCI spike

The Phase 0 spike answers the packaging questions before any typed
specification or assembler exists. It is throwaway prototype code under
`poc/rfd3-phase0/` driven by `scripts/rfd3-phase0-spike.sh`; the Phase 1 Rust
assembler replaces the prototype. The prototype deliberately reuses
standard-library primitives (`json`, `tarfile`, `gzip`, `hashlib`) rather than
hand-rolling container parsing, and it never extracts a layer with the host
`tar` program.

The checked-in command is:

[source,shell]
----
.agents/dev ./scripts/rfd3-phase0-spike.sh
----

It compiles one external static executable and one dynamically linked
executable from `poc/rfd3-workload/main.c`, builds four local OCI image
layouts, applies representative layers twice, normalizes every source into a
content-addressed store, removes the entire generated source tree, and only
then records and passively replays each workload through one guest supervisor.
The guest supervisor is a spike, not the Phase 2 agent: it launches the packaged
program in a private `chroot`, feeds it a fixed command file, drains its output
while it runs, and then kills and reaps every remaining guest process. It
exposes no command protocol, makes no application-protocol assertions, and does
not yet apply a normalized launch configuration.

Every workload printed the same bounded exchange, and both replays of each
source were byte-identical to its record:

[source,text]
----
ready version=1
echo value=asymmetric_42
state value=fresh
descendant state=escaped
stopped status=0
supervisor source=<source>
supervisor workload_status=0
supervisor cleanup_reaped=1
supervisor output_bytes=101
SIMFERRET_PHASE0_SUPERVISOR_OK version=1
----

`cleanup_reaped=1` is the escaped double-forked session leader the fixture
creates: it survives the primary process, retains the workload output
descriptor, and is killed and reaped only through the supervisor's
whole-guest barrier. The output stream reached end of file only after that
barrier, so no workload descriptor survived it.

=== Layer semantics and canonical identity

The layer-semantics layout applies a base layer and an upper layer that
exercise directory metadata updates, content and metadata replacement, a
whiteout that removes a lower entry with no same-layer addition, a whiteout
whose same-layer addition must survive, an opaque directory, a lower file
replaced by an opaque directory, new nested directories, a relative symbolic
link that escapes upward but stays inside the root, and a whiteout for a path
that does not exist. The `opt` opaque marker and the root-opacity marker both
appear *after* the additions they coexist with, so an implementation that
applied markers in archive order would delete same-layer additions and change
the result. The `etc/swap` marker deliberately precedes its addition, because
it also covers a lower file replaced by an opaque directory.

Applying it twice, in separate processes with different `PYTHONHASHSEED`
values, produced one canonical digest over 19 entries and byte-identical
materialized trees:

[source,text]
----
semantics_canonical_digest=38782e7c828a0eec4ac79dc20ab30bf6ab3c0b10c3048b15265db4b0d74e27f0
semantics_entries=19
semantics_expanded_bytes=70808
semantics_duration_ns=141189175
semantics_reapply_equal=true
----

The observed final tree confirms each rule: `etc/` moved from mode `0755` to
`0750`; `etc/config` was replaced by upper content with new metadata;
`etc/remove-me` is the upper addition at mode `0600`, so the whiteout removed
only the lower-layer entry; `etc/pure-delete` is absent, so a whiteout with no
same-layer addition removes its lower entry; `etc/swap` is a directory
containing `new`, so a lower file can be replaced by an opaque directory;
`opt/keep`, `opt/drop`, and `opt/nested` are gone while `opt/new` survives the
opaque marker that appears after it; `srv/opaque/lower` is untouched by an
unrelated opaque marker; and both symbolic links kept their exact targets.

The canonical digest also covers numeric ownership, which the host staging tree
cannot reproduce because the spike runs unprivileged. The fixture sets `etc/` to
canonical `2000:2000`; the materialized tree shows the host owner instead. That
distinction is why the regression test asserts mode and modification time and
not ownership, and it is why guest-visible nonzero ownership remains a Phase 2
assembler and Phase 4 verification concern. Symlink modes are normalized to
`0777` in the canonical model, because a Linux symbolic link has no settable
mode, so the identity never claims a mode the guest cannot have.

=== Root-level opacity

A separate two-layer layout covers the root directory, because a root-level
opaque marker in the main fixture would erase the executable. The base layer
holds `bin/simferret-workload-fixture`, `keep/lower`, `drop`, and `dir/child`;
the upper layer re-adds `bin`, `keep/upper`, and finally a root
`.wh..wh..opq`. The resulting tree is exactly the upper layer's own additions:

[source,text]
----
opacity_tree=./bin ./bin/simferret-workload-fixture ./keep ./keep/upper
----

That proves root opacity removes lower-layer descendants rather than nothing,
and that it leaves same-layer additions alone even though the marker is last.

=== Content-addressed closure and live-source removal

Each source produces one raw closure and one derived entry. Raw evidence is the
opened executable plus the canonical specification for a binary, and
`oci-layout`, `index.json`, the selected manifest, the config, and each stored
layer for OCI. The prototype re-derives the canonical tree from the raw objects
on every replay and refuses to proceed when a raw object is missing, corrupt, or
inconsistent with its recorded size and digest.

Replay also verifies more than the tree. The binary specification is re-parsed
from its verified raw object rather than read back from the closure record, so
editing the record cannot change the launch the store reproduces; the
re-derived launch, layer evidence, policy versions, and limits are each compared
against the closure; and the closure record is pinned by a digested lock, so
editing it is detected even when the edit is internally consistent. The lock
belongs in the run manifest in the Phase 1 assembler; the store-sidecar lock is
the prototype equivalent. It is a corruption detector, not an authentication
mechanism: replacing the raw objects, the closure, the sidecar, and the derived
lock consistently would produce another self-consistent recording, which is the
same limitation RFD 3 records for content digests generally.

==== Replay divergence under the host-coupled model

That claim has an observed exception, and it matters to the model question rather
than to this increment's construction. A continuous-integration run of the Phase 4
acceptance (which runs this demonstration) failed in the binary source's first
replay with

[source,text]
----
qemu-system-x86_64: Missing character write event in the replay log
  (insn total 2362086659/74 left, event 5431704 is EVENT_INSTRUCTION)
----

and a failure bundle recording `error_kind: early-termination`, `error: truncated
serial event frame`, `stage: execution`, and `backend_mode: replay`.

What it means. The replaying guest performed a character write at an instruction
position where the replay log's next event is an instruction event. QEMU's
`replay_char_write_event_load()` accepts only `EVENT_CHAR_WRITE` there, so the
replaying guest's instruction stream had diverged from the recording's before
that point. The run was recorded under the model the product launches today,
`shift=auto`, where the guest's virtual clock is coupled to host real time, so
the number of instructions the guest executes between its serial writes depends
on how the host schedules it.

What it rules out. A truncated or incomplete recording is ruled out by the
message rather than by a digest: the log still held a well-formed event at that
position, where a truncated log fails while reading one. The recording's own log
digest could not be compared against its manifest for this run, because the
uploaded bundle carries the replay's logs and `failure.json` only; a replay of a
recording whose log was truncated would fail differently, and no such failure has
been observed. A QEMU defect is not ruled out, but the same binary replays the
same demonstration correctly under the pinned model below, and the message is the
machinery reporting a divergence rather than misreading an intact log.

Rate and reproduction. One failure in the continuous-integration history of this
step (run 35713214491; the neighbouring revisions of the same branch passed it),
and no failure in the local phase 3 acceptance run under deliberate load (eight
CPU consumers and three parallel QEMU guests) that was recorded for comparison.
The failure is rare rather than impossible, so a green run is not evidence that
the recording is reproducible.

The pinned model. The same demonstration, recorded and replayed under
`shift=4,sleep=off` with the spike QEMU of RFD 4
(`poc/time-model/qemu-nosleep-replay-flush.patch`), completed with both replays
matching under the same load shape, and the Phase 4 acceptance under that model
passes. Under `shift=4,sleep=off` the guest's virtual time is a function of its
instruction count, so the positions this failure depends on cannot move with host
scheduling. That is evidence for the pin, not proof that `shift=auto` is the only
model that can diverge: the failure is too rare to bound a rate from one sample.

Guards, proposed rather than built. Validate the recorded log's integrity against
the manifest before replaying, so an incomplete recording is reported as an
incomplete recording rather than as a guest divergence; and classify QEMU's
replay-divergence message as a typed error, because the frame-level
`truncated serial event frame` this currently surfaces as points at the symptom
rather than at the divergence. Neither guard would make a host-coupled recording
reproducible, which is the model question RFD 4 records.

The rejections above are the Phase 0 prototype's observed output, kept verbatim
as spike evidence. The shipped assembler refuses the same constructs with
value-free diagnostics: every layer rejection names the layer and member position
plus a fixed category (`absolute layer paths are unsupported`, `layer paths must
not contain '..' components`, `a layer contains duplicate normalized paths`,
`a layer marker traverses a symbolic link`, `layer 0 member 3 has an unsupported
mode`, `layer 0 member 3 is a hard link, which is unsupported`, and so on), never
the path, media type, link target, or raw header field that caused it. The tar
parser's own errors, which quote the pathname and the invalid numeric field, are
reduced to fixed context for the same reason.

The prototype also rejects FIFOs, sockets, sparse files, empty or malformed
digests, empty manifests, numeric metadata outside its serializable range, an
opaque marker whose parent is still a non-directory after the layer is applied,
and invalid launch fields such as non-numeric or root credentials, duplicate
environment names, non-absolute working directories, volumes, and stop signals.
Its limits are prototype-local policy: 64 MiB stored layer, 256 MiB expanded
layer, 16 MiB file, 4,096 entries, 16 layers, 1,024-byte path, 4,096-byte
symbolic link target, 40 symbolic link expansions, 64 raw closure objects, and
a 4 MiB bound on cache metadata files. Phase 1 replaces them with the limits the
RFD fixes. The cache bound matters because replay reads `closure.json`,
`tree.json`, and the derived lock through the same bounded beneath-root reader
as raw objects, and a materialized tree containing a special file is rejected
rather than read.

Two deviations from the RFD's stated profile are deliberate and recorded for
Phase 1. Python's `tarfile` consumes GNU `longname` and `longlink` records
transparently, so a layer using them is accepted even though the prototype
rejects PAX headers; detecting the physical extension records would mean
re-implementing tar parsing, which the RFD forbids. And descriptor `urls` and
embedded `data` are not yet rejected, because the prototype only ever opens
local `blobs/sha256/` paths; that is a Phase 1 rejection requirement, not a
safety gap, since nothing is fetched.

The derived entry is also shaped differently from the RFD: it contains
`tree.json`, the materialized tree, and a lock naming the closure, while the
RFD describes a derived entry that names its complete raw closure. The
relationship is recorded, but in the closure record rather than in the derived
entry, so Phase 1 should decide which direction the RFD intends.

=== Rust primitive selection

The Phase 1 assembler should select existing primitives before writing custom
format handling. The spike evaluated the pinned workspace dependencies and the
candidate crates:

[cols="1,1,3",options="header"]
|===
| Concern | Selection | Rationale

| JSON
| `serde` 1.0 and `serde_json` 1.0
| Already pinned in the workspace; serde's default of ignoring unknown fields
  matches the OCI forward-compatibility requirement without relaxing explicit
  rejection of unsupported selected values.

| Digests
| `sha2` 0.10
| Already pinned; supplies descriptor, DiffID, and canonical-identity SHA-256
  without a C dependency.

| Gzip
| `flate2` 1.1 with `rust_backend`
| Already pinned with the pure-Rust backend, so layer decompression is
  reproducible and does not link a system zlib. Decompression still needs an
  explicit expanded-byte bound because the reader can expand past a limit.

| Tar
| `tar` 0.4
| Streams USTAR/PAX entries without extracting them and exposes entry type,
  mode, ownership, link target, and size so the assembler can reject hard
  links, devices, sparse files, and setuid modes itself. The prototype's GNU
  longname experience is the reason to inspect physical extension records
  deliberately rather than rely on a library's convenience behavior.

| Safe filesystem access
| `rustix` 1.1
| Exposes `openat`-style calls with `O_NOFOLLOW`, `O_NONBLOCK`, and directory
  file descriptors so every source read and staging write stays beneath one
  opened root. `O_NONBLOCK` is required: a blocking open on a FIFO waits for a
  writer instead of rejecting the special file. `cap-std` 4.0 is the
  alternative but is a larger abstraction than this increment needs.

| OCI types
| Minimal `serde` structs, with `oci-spec` 0.10 as a reference
| The bounded profile needs strict rejection of unsupported selected values and
  deliberate ignoring of unrelated fields, which minimal structs express
  directly. `oci-spec` remains the reference for media-type and field naming.
|===

None of these crates is added to the workspace in Phase 0. The prototype is
Python so that a wrong policy costs a spike edit instead of an assembler
rewrite; Phase 1 adopts the selection above and its pinned versions.

=== Phase 0 regression tests

The focused command is:

[source,shell]
----
.agents/dev ./scripts/rfd3-phase0-spike-test.sh
----

It fakes the QEMU invocation and checks that one successful run records exactly
three QEMU invocations per source, removes the whole generated source tree, and
writes the expected evidence keys. The fake refuses to start while a `sources`
directory exists, so a regression that moved deletion after QEMU would fail
rather than pass. It fails divergent, incomplete, and infrastructure-failure
guest output, and it requires invalid duration bounds to fail before QEMU
starts.

It then exercises the prototype directly: the layer-semantics digest and tree
are stable and include a pure-deletion whiteout, an opaque directory after its
same-layer addition, and a file replaced by an opaque directory; root-level
opacity produces exactly the upper layer's additions; the binary and static OCI
sources converge; repeated layout generation is byte-stable; a missing, corrupt,
or tampered raw object, a tampered derived entry, an edited closure record, a
closure whose launch no longer matches its specification, a closure missing its
specification object, an oversized closure record, and a special file inside a
cached tree all fail materialization; a symbolic-link source is rejected; a
whiteout whose parent the same layer replaces with a symbolic link is accepted
while a marker inside a lower-layer symbolic link is refused; and every
unsupported construct is refused without partial output.

== Phase 1 typed specification and canonical assembler

Phase 1 replaces the Python prototype with `crates/simferret/src/workload/`: a
strict TOML specification, a bounded beneath-root reader, an OCI image-layout
normalizer, a canonical tree and identity, and a raw closure plus derived cache
store. It selects the Rust primitives the Phase 0 spike recommended: `serde` and
`serde_json` for JSON, `sha2` for digests, `flate2` with `rust_backend` for
gzip, `tar` 0.4 for layer records, and `rustix` 1.1 for `openat`-style access
with `O_NOFOLLOW`, `O_NONBLOCK`, and directory descriptors. The prototype is no
longer on any execution path.

=== Resolved Phase 0 deviations

* GNU `longname` and `longlink` records, PAX `x` and `g` records, hard links,
  devices, FIFOs, sockets, sparse files, setuid and setgid modes, and unknown
  tar type bytes are each rejected by inspecting the physical record type with
  raw iteration. The prototype accepted GNU long names because Python's
  `tarfile` resolved them transparently.
* Selected descriptors that declare `urls` or embedded `data` are rejected
  before the referenced content is opened. Unselected descriptors are still
  ignored whatever they contain, so forward compatibility is preserved.
* The derived entry names its complete raw closure. `derived/<canonical>/lock.json`
  records the closure digest, the canonical digest, and the tree and template
  digests, and verification refuses a derived entry that does not name the
  closure being replayed. The Phase 0 record-direction question is resolved in
  favor of the RFD's "each derived entry names its complete raw closure".

=== Bounded profile

The Phase 0 prototype's limits are adopted as fixed constants: 1 MiB
specification, layout, manifest, and config; 4 MiB index; 64 MiB stored layer;
256 MiB expanded layer and canonical expanded bytes; 16 MiB file; 4,096 entries
per layer; 16 layers; 1,024-byte path; 4,096-byte link target; 40 link
expansions; 64 raw closure objects; 32,768 canonical entries; 4 MiB cache
metadata; 256 arguments and environment entries; 4 KiB per argument and
environment entry; and 64 KiB total environment. Every bound is recorded in the
raw closure, so changing one changes the workload identity and a recording made
under other limits fails verification rather than being reinterpreted.

Two further profile decisions are recorded here. Modification times are limited
to the unsigned 32-bit whole-second range because the guest template is a `newc`
CPIO archive, and a timestamp the template cannot encode is rejected rather than
truncated. A standalone binary installs at the one fixed canonical path
`/bin/simferret-workload`; binary specifications therefore carry no install path
and no auxiliary file tree.

The Phase 1 store holds exactly one workload closure and refuses to replace it
with a different one, so the derived entry can name its closure unambiguously.
Reusing a shared store across different workloads is deferred to the Phase 3 run
integration, which will name closures by digest.

=== Review hardening

A pre-merge review of the Phase 1 implementation found and fixed nine issues.
Each fix carries a regression test:

* The guest template now emits the root entry first and requires the canonical
  root to be a directory. Initramfs extraction does not create missing parents,
  so a path such as `!early`, which sorts before the `.` root sentinel, would
  otherwise have been dropped during extraction. Covered by
  `template_emits_the_root_before_paths_that_sort_before_it`,
  `template_emits_the_root_first_with_canonical_metadata`,
  `a_non_directory_root_is_rejected`, and `a_non_directory_root_has_no_template`.
* `Root::sha256_file` validates the file type and size on the same descriptor it
  hashes, so a FIFO or device in the derived entry is refused instead of read.
  Covered by `a_fifo_in_the_store_is_rejected`.
* Source locators are traversed component-wise through the specification
  directory descriptor, so a symlinked layout component is refused, and the
  specification open is non-blocking and type-checked. Covered by
  `a_symlinked_layout_locator_is_rejected` and
  `a_fifo_specification_does_not_block`.
* Store directories are created mode `0700` and store files mode `0600`, as the
  RFD requires for private artifacts, independently of the ambient umask.
  Covered by `store_artifacts_are_owner_only`; the evidence script asserts the
  same under `umask 022`.
* Canonical entry and expanded-byte bounds are enforced after every applied
  layer and on replay, not only at publication, so a hostile multi-layer image
  cannot accumulate an unbounded intermediate tree. Covered by
  `an_over_entry_limit_tree_is_rejected_during_construction`,
  `an_expanded_layer_beyond_the_limit_is_rejected`, and

* The combined OCI `Entrypoint` and `Cmd` vector is validated against the shared
  argument bounds, and `Env: null` is treated as empty. Covered by

* The raw closure is published last, after the derived entry it names, and an

* A populated `raw/sha256` directory is validated before objects are written or

  per-artifact check did not cover a weakened object directory in an
  already-populated store. Covered by an added case in

* A metadata-only USTAR member that declares a data record is rejected. The raw
  iterator advances by the declared size, so a directory or symbolic link with a
  nonzero size would have silently dropped physical bytes while the parsed tree
  stayed valid. Covered by
  `a_metadata_only_member_with_a_data_record_is_rejected`.
* The evidence script's store inventory is written to a private file and `find`'s
  own status is checked, so a failed or partial enumeration can no longer pass
  silently, and the remaining source, executable, layout, and store-size
  measurements are hoisted out of the report block.

The moved-install-path regression was also corrected: the retained install path

normalizer already rejects, so it did not reach the profile invariant. With the
guard removed the recording is still rejected, but later, by the launch-identity
comparison; the test's diagnostic assertion is what pins the profile invariant.

A fifth review round closed two more gaps:

* The evidence script's field reader propagates a failing reader status
  explicitly, because `errexit` is disabled inside a command substitution, so a
  reader that emits a usable field and then fails would otherwise be accepted.
  The script now injects exactly that fault on every run and requires it to
  abort.
* Layer archives must end with the two zero blocks POSIX requires after the last
  member. The pinned raw iterator stops at the first zero block or at end of
  input, so a truncated archive, or a member hidden behind a single zero block,
  would have been parsed as a shorter valid archive. Covered by
  `a_layer_without_a_valid_end_of_archive_marker_is_rejected`.

Two profile notes are recorded rather than fixed. A nonzero directory size is a
permitted USTAR directory-allocation hint, but this profile refuses it because
the pinned iterator cannot distinguish it from a payload; supporting it later
requires correct header-only framing. And publication is atomic with respect to
process failure, not to power loss: staging files are synced, but the store
directories are not, so durable crash recovery remains follow-up work.

A sixth review round closed one more malformed-input acceptance. The ELF
validator now requires the native 56-byte program-header size and a program table
no larger than the guest loader's 64 KiB limit, instead of only rejecting a
header smaller than the native size. Covered by the
`wrong-program-header-size` and `oversized-program-table` cases in
`unsupported_binary_inputs_are_rejected`; both inputs were confirmed to be
accepted before the fix.

A seventh review round extended the same validator with the guest's mapping
contract:

* A file-backed loadable segment's file offset and virtual address must share a
  page offset, because the guest maps it from `address - (address % page)`; a
  mismatch fails only after the process image has already been replaced.
* A loadable segment's virtual address range, and the entry point, must stay
  below the guest's 47-bit user address-space limit, matching the loader's own
  address checks.

The test ELF fixture now places its payload at a page-congruent address and
declares an entry point, so each negative case violates one invariant instead of
passing for an incidental reason. Covered by the `misaligned-loadable-segment`,
`loadable-segment-outside-address-space`, and `entry-outside-address-space` cases
in `unsupported_binary_inputs_are_rejected`, and by
`a_program_table_at_the_loader_limit_is_accepted`, which pins the 65,520-byte
boundary so the table limit cannot drift to `>=`. The compiled acceptance fixture
was rechecked against the new rules: its eight program headers, 448-byte table,
entry point, and four page-congruent loadable segments all satisfy them.

An eighth review round corrected the address-space comparison and closed two
further loader-refused inputs:

* A loadable segment's exclusive end may equal the guest's user address-space
  limit; only a larger end is refused. The limit is the four-level value because
  the pinned guest CPU model does not expose five-level paging, and the entry
  bound is an assembly-time necessary condition rather than a guarantee for a
  relocated image, whose final entry also depends on the runtime load bias.
* A fixed-address executable may not map below the guest's minimum mapping
  address, which the pinned kernel keeps at its default and the unprivileged
  workload cannot lower. Relocated images may legitimately map at zero, so the
  rule applies to fixed-address executables only.
* A relocated image must have a nonzero aggregate mapping span, computed from its
  first loadable segment's page start to its last segment's end, as the loader
  computes it.

Covered by the `fixed-segment-below-minimum-mapping` and
`relocated-image-without-mapping-span` cases in
`unsupported_binary_inputs_are_rejected` and by
`elf_address_space_boundaries_are_enforced_exactly`, which accepts a segment end
exactly at the limit, a fixed mapping exactly at the minimum mapping address, and
a relocated image with a mapping span, and refuses one page past the limit.

A ninth review round replaced the header-order mapping-span rule with the
loader's actual requirement, after checking the pinned kernel's loader source:

* A relocated image must begin with a file-backed loadable segment, because that
  is the mapping the loader uses to choose its load base. A first segment with no
  file content is instead mapped anonymously at the base the loader has not
  chosen yet, which the unprivileged guest refuses. A file-backed first segment
  also makes the aggregate mapping span nonzero, which the loader requires before
  it relocates anything, so the separate span test is subsumed and was removed.
  The earlier header-order endpoint comparison could additionally reject a layout
  the loader accepts, because the loader measures the span from the lowest page
  start to the highest segment end.
* A relocated image may not request a power-of-two alignment at least as large as
  the user address space, because the loader then rounds its chosen base to zero
  and retries at a fixed address the guest refuses. Non-power-of-two alignments
  are ignored rather than rejected.
* A fixed-address segment with no memory content requests no mapping, so it is
  exempt from the minimum mapping address.

The first two rules above applied only to relocated images and were removed when
the profile was narrowed to fixed-address executables in the next round; only the
no-op-load exemption remains.

A tenth review round then closed the increment by narrowing the profile instead
of extending that model. Simulating `ET_DYN` relocation was proving unbounded:
each round produced another source-provable way for the loader to refuse an image
that assembly had accepted, most recently a relocated image whose single
reservation covered the whole user address space. The standalone binary profile
now accepts only a fixed-address (`ET_EXEC`) image, because a relocated image's
load base, entry address, and mapping alignment are chosen by the guest loader at
exec time, so assembly cannot establish that it would load. A static PIE is
refused with the diagnostic "binary workload must be a fixed-address executable
ELF file, not a relocatable, core, or static-PIE image", and the same bytes are
still accepted from an OCI source, where loading is left to the guest. Covered by
`a_relocated_binary_is_refused_with_a_profile_diagnostic` and
`the_same_relocated_executable_is_accepted_from_an_oci_source`; the `ET_EXEC`
boundary, no-op-load, and address-space cases remain as they were.

Each of these tests was confirmed to fail when its fix is reverted, so none of
them asserts a merely incidental error.

== Phase 2 guest process runtime

Phase 2 replaces the throwaway Phase 0 supervisor with `crates/simferret/src/runtime.rs`
and extends the versioned control protocol with the process commands. The PID-1
agent stays outside an immutable workload template at `/workload`; for every
invocation it materializes a fresh writable root under `/run/simferret`, applies
the versioned overlay, and supervises exactly one child in a private filesystem
root.

The guest image assembler now appends the canonical workload template below that
reserved root. `Tree::template_entries` emits the same `newc` records as
`Tree::template` without the trailing marker, so the workload template and the
agent's own entries concatenate into one initramfs archive. A unit test decodes
the resulting archive and requires `workload` and `workload/bin/app` to be
present, `init`, `bin/busybox`, and `modules/mii.ko` to stay outside it, and
exactly one trailer. The run flow still passes no template, because selecting the
workload and recording its identity in the run manifest belongs to Phase 3.

=== Runtime profile

The runtime enforces the RFD's launch and lifecycle rules:

* The template is validated before any invocation. A package entry at `/tmp` or
  `/dev` must be a directory and is replaced by the overlay; a non-directory
  entry anywhere below those paths is rejected as an overlay collision. Special
  files, entries beyond the canonical view bound, and paths beyond the canonical
  path bound are rejected before any root is created. The runtime reuses the
  assembler's constants and counts the template root the same way, so the two
  phases agree on the template bounds and the runtime never rejects a template
  for exceeding a bound the assembler allowed.

  Overlay compatibility is a separate rule and is enforced only at the runtime
  boundary: the assembler does not yet reject a package entry that collides with
  the overlay, nor a launch path that overlay replacement invalidates. A template
  whose package entry collides is refused when the runtime is constructed, so the
  agent reports an infrastructure error rather than a `launch-failed` event; a
  launch path that overlay replacement invalidates is refused per invocation as a
  typed `launch-failed` event. Moving both checks into assembly is listed for
  Phase 3.
* Each invocation copies the template bytes and canonical metadata into a new
  root, skipping the `/tmp` and `/dev` subtrees so the overlay replaces them
  instead of merging with them, then synthesizes `/tmp` as a root-owned
  mode-`01777` directory, `/dev` as a root-owned mode-`0755` directory, and
  `/dev/null` and `/dev/zero` as mode-`0666` character devices `1:3` and `1:5`.
  The canonical root metadata is applied after the overlay, so creating it cannot
  change the recorded directory timestamps. The root is removed at the cleanup
  barrier, so no invocation can observe a previous one.
* The child receives only fresh standard pipes; every other inherited descriptor
  is closed, covering the whole descriptor table in two `close_range` calls so a
  descriptor above any scan cap cannot leak. A table scan is not an equivalent
  fallback, because lowering `RLIMIT_NOFILE` does not close descriptors that are
  already open; setup therefore fails with a typed `launch-failed` event rather
  than continuing with a descriptor that might reach the workload. The
  close-on-exec flag is cleared explicitly on the standard descriptors, because
  `dup2` leaves it alone when both descriptors are equal. The child then restores
  the default `SIGPIPE` disposition that Rust installs for itself, changes root,
  changes to the normalized working directory, clears supplementary groups, sets
  `no_new_privs`, applies the nonzero GID and UID, and executes the exact
  argument vector without a shell. Setup failures are reported through a
  close-on-exec pipe as typed `launch-failed` events, so a successful `execve` is
  unambiguous.
* Launch validation is one shared rule set, applied both when the assembler
  normalizes a binary or OCI source and again when the runtime accepts an
  invocation: the executable and the working directory must be absolute in-root
  paths, the first argument must name an absolute in-root path without being
  required to equal the executed path, and the argument and environment vectors
  are bounded. Diagnostics name the field and never echo a caller-supplied
  argument or environment value.
* The versioned process commands are `start`, `stdin-write`, `stdin-eof`, and
  `terminate`. `stdin-write` carries an invocation identifier, a strictly
  contiguous byte offset, and bounded hexadecimal exact bytes; `terminate` is an
  unconditional `SIGKILL` independent of any OCI stop signal.
* Live stdout and stderr frames carry the invocation, the stream, a per-stream
  byte offset, one monotonic cross-stream sequence number, and exact bytes. The
  exit record independently reports per-stream totals, SHA-256 digests, and the
  number of frames emitted. A per-frame or per-invocation limit overflow, a
  non-contiguous offset, and a control or pipe transport failure are fatal: the
  invocation is killed and the agent reports an infrastructure error rather than
  a workload property. One batch offers each stream at most half of the remaining
  budget, so a continuously readable stream cannot starve the other, while a
  single ready stream still drains the whole budget across the batch. A process
  exit record whose code or signal is outside the Linux range cannot be accepted
  by a typed frame reader. The runtime's own producer uses the wait-status macros,
  so it only ever encodes values inside the range.
* On primary exit or termination the runtime signals every member of the active
  invocation, reaps until only the agent remains, and drains both pipes to end of
  file before emitting `cleanup-complete`. The reap and the signal are scoped to
  the invocation: in guest scope they cover the whole process table, and in
  process-group scope only the invocation's own process group, so a host test
  cannot disturb or consume an unrelated child. Each advance reaps before it
  services input, so an already-exited primary moves straight into the barrier
  instead of a write to a pipe whose readers are gone being reported as an
  infrastructure failure. `terminate` discards queued input and closes the
  child's standard input before it signals, for the same reason, and input is
  refused once termination is requested.

  Root removal is explicit and fallible on every path that created a root,
  including a failed start: a removal failure is reported alongside the launch
  failure, and a root that could not be removed is remembered so the next start
  retries its removal and is refused while the path survives. The single-workload
  slot also stays occupied when the barrier cannot remove its root, so a later
  invocation can never start on top of a root that is still on disk. A new
  `start` is refused until that barrier completes. The agent
  reports process and byte facts only; application protocol interpretation
  remains in the host scenario checker.

=== Deliberate limits

The host tests exercise the process-group scope for the ordinary descendant and
the guest-wide scope only inside a PID namespace, because the guest-wide sweep
must not signal unrelated host processes. In process-group scope the reap is
scoped to the invocation's own process group, so a host test cannot lose an
unrelated child it still needs to observe. Application protocol parsing, workload
assertions, and the run manifest's workload identity remain Phase 3 work, and so
does a recorded QEMU acceptance of this runtime: the checked-in phase 2 evidence
is the host PID-namespace script above. The runtime reports no throughput or
security claim beyond the accepted profile.

== Phase 3 scenario and passive replay integration

Phase 3 wires the assembled workload into the run pipeline. `simferret run` gains
an optional `--workload SPECIFICATION`; when it is present the scenario is parsed
as the versioned workload-driven acceptance scenario and the packaged workload,
not the agent, originates every recorded request. The normalized workload
identity is recorded in the run manifest and in a private `workload.lock`
artifact, and replay re-derives it from the raw closure before QEMU starts.

The host checker (`crates/simferret/src/checker.rs`) owns all application
meaning. It folds the recorded events into a process and stream trace, checks
each invocation's reconstructed stdout and stderr against the exit record's
independently reported totals and digests, matches the ordered response lines to
the recorded input commands, and evaluates five properties: `process_safety`,
`response_integrity`, `controlled_outage`, `restoration`, and
`bounded_recovery`. The guest agent still reports process and byte facts only.

The acceptance fixture is the checked-in `poc/rfd3-workload/main.c`. It answers
`echo`, reports whether its root already carried a previous invocation's marker,
spawns an escaped `setsid` descendant that retains the output descriptor, fetches
a named fixture file over TFTP from `10.0.2.2`, and exits on end of input. The
same source is compiled once and packaged three ways:

* a standalone fixed-address static binary workload;
* a local `linux/amd64` OCI image layout carrying the same executable at the
  binary profile's canonical install path, so both forms converge on one
  canonical tree; and
* a focused dynamically linked OCI layout whose executable, interpreter
  (`/lib64/ld-linux-x86-64.so.2`), and `libc.so.6` closure exist only in the
  image.

The seeded workload choice plan adds a process-fault request index alongside the
outage and restoration indices, and requires at least four requests so the fault
is always strictly inside the sequence and distinct from both transitions.

=== Two integration fixes

Two pre-existing behaviours only became observable once a workload was live, and
both were fixed in this phase:

* `Runtime::terminate` closed the child's standard input before signalling. A
  workload that treats end of input as a clean exit left the process before the
  fixed `SIGKILL` landed, so the exit record reported `exited` instead of the
  requested termination. The signal is now delivered first and the queued input
  is dropped in the same critical section, so the command is unconditional as
  documented and no later poll can write to a pipe whose readers are gone.
* The host command writer wrote one byte and waited for one acknowledgement per
  byte. That round trip costs roughly 30ms once a workload is live under the
  pinned TCG/icount profile, so a 250-byte workload command could not complete
  inside the command deadline. The writer now writes bounded 16-byte chunks (the
  guest UART FIFO depth) and waits for the same number of acknowledgements, so
  the guest still acknowledges every byte it consumes while the round trip is
  paid once per chunk. Record duration dropped from a timeout to about 14s and
  replay to about 22s. A larger chunk overran the guest serial FIFO and
  corrupted the control stream, which is why the chunk is pinned to the FIFO
  depth.

=== Assembly-time overlay compatibility and artifact classification

The runtime overlay rules moved into assembly: `validate_overlay_compatibility`
refuses a canonical tree with a non-directory entry at or below `/tmp` or
`/dev`, and refuses a launch executable or working directory the overlay
replacement would invalidate. Assembly and replay both apply it, so a template
the runtime would refuse is never published and replay re-derives the same
decision from the raw closure instead of failing at the runtime boundary.

The run directory and the host-written run artifacts are owner-only (`0700` and
`0600`): they carry the recorded launch environment, the exact workload stream
bytes, and the private replay closure. The shareable failure bundle is a separate
directory and carries bounded protocol metadata, counts, digests, and typed
errors only; a regression test asserts that neither the recorded environment
value nor a recorded workload output line appears anywhere in it. The sanitizer
replaces every private path it knows — the staging directory, the runtime
directory, and the whole runs directory, which holds the workload store, the
guest image cache, and the run artifacts — with a fixed `<private-path>` label,
so a diagnostic that names one of them cannot carry the operator's own path into
the shareable report. Every representation is covered, because the path can be
relative, QEMU comma-escaped, or Rust debug-escaped, and the replacement only
applies at a path boundary so an unrelated longer name that shares a prefix
survives. The store and cache rejections do not render the path at all: they name
the object with a fixed label, and the record path derives the store and cache
from the canonicalized runs directory.

=== Adversarial review hardening

The first adversarial review of the Phase 3 stack found fifteen issues, and every
one of them was addressed in the same phase rather than deferred:

* *Value-free diagnostics.* Every divergence, envelope, and parser diagnostic now
  names the event kind and its non-secret coordinates (invocation, stream,
  offsets, byte lengths, digests) instead of formatting whole events, commands,
  or environment entries. A divergence or a malformed `NAME=VALUE` entry can no
  longer put the recorded launch environment or exact stream bytes into
  `failure.json` or the CLI error text. `Event::kind`/`Event::describe` and
  `Command::kind`/`Command::describe` are the single source of those
  descriptions, and a protocol unit test pins the tag names against the wire form
  and asserts that no marker value survives. Parser failures are reduced by
  `crates/simferret/src/diagnostics.rs`: a private artifact reports only a
  category and a location, and a user-authored specification or scenario reports
  only a location as well, because both serde and TOML format the offending value
  with escaping a redactor cannot reliably undo. The generic frame readers, the
  retained canonical specification, and the surplus-event diagnostic all use the
  same reduction, and canaries place the secret in the offending value itself,
  including one that embeds the delimiter the parser quotes it with. Semantic
  launch validation is value-free too: the user, working directory, executable
  argument, digest, and manifest-descriptor diagnostics name the field and the
  expected shape rather than the value, the working-directory and executable
  paths map the layer-path helper's value-bearing error onto a field-specific
  one, and the recorded OCI manifest digest is validated before it can be named.
  Record-path canaries assert that neither the CLI text nor the shareable failure
  bundle carries a marker placed in those fields, including a traversal path.
  Guest-reported free-form strings are not descriptions either: a diverging
  `network-configured`, `outage-activated`, `network-restored`, or request event
  can carry any bytes in its gateway, peer, rule, or request-identifier field, so
  `Event::describe` names the tag, the request phase, the typed error, and the
  numeric coordinates only, and the fault-transition diagnostics in
  `failure.json` take their peer and rule from the validated network profile the
  run configured instead of from the event. The protocol canary places a marker
  in each of those fields, and an end-to-end record canary asserts that a rejected
  activation's strings appear in neither the CLI text nor the bundle. The store's
  raw-closure reader follows the same rule: an unknown object role and an object
  that exceeds its policy limit are named by their position, so a tampered
  `closure.json` cannot carry a marker into the CLI text or the failure bundle of
  a replay that rejects it. Three more semantic rejections follow the same rule:
  the overlay collision names the fixed `/tmp` or `/dev` subtree instead of the
  colliding entry path, the replay scenario-name comparison names the
  disagreement instead of either name, and a repeated raw-closure role names the
  object's position. The layer reader is value-free as well: a rejected member
  names the layer and member position plus a fixed category, never the path, the
  symbolic-link target, the media type, or a raw header field, and the tar
  parser's own errors are reduced to fixed context. The replay identity
  comparisons and the version check name the differing field only, because a
  recorded identity can carry an arbitrary string or a private host path. The
  binary and OCI assembly boundaries reduce a source-locator failure to the field
  it belongs to and the error's category, because the root's own diagnostics
  quote the locator and it is a user-authored specification value.
* *Owner-only image cache.* The `.images` cache is created `0700` with `0600`
  entries, and a reused entry is validated before it is opened: its type,
  ownership, and mode are checked first and repaired where possible, then it is
  hashed through the same `O_NOFOLLOW | O_NONBLOCK` reader the replay inputs use,
  so a writer-less FIFO or a device node is rejected instead of blocking the run.
* *Validated asynchronous events.* The driver folds events it does not
  synchronously await, so the checker validates them instead: a start, exit,
  termination, cleanup, launch failure, or input acknowledgement for an unknown
  invocation, an input acknowledgement after the invocation was terminated, a
  duplicate start, exit, termination, cleanup, network configuration, activation,
  or restoration, a termination after its exit, a cleanup before its exit or
  without reaping a process, a configuration that is not the fixed private
  profile, and an activation without its prohibition rule are all
  stream-structure violations. A launch failure is an alternative outcome to a
  start record rather than an event of a running invocation, so it is retained for
  an invocation that never started; it may still not repeat, and it may not arrive
  after the invocation exited. `process_safety` also requires exactly one
  termination record, for the first invocation, which is what the acceptance
  profile performs.
* *Complete stream evaluation.* Per-invocation offset, sequence, and input-stream
  violations are now evaluated alongside the trace-level ones; sequences must
  start at one and stay contiguous; each accepted input must advance the accepted
  offset by exactly its byte count and name a distinct later command; an
  end-of-input must be unique and last; every response line but the startup line
  must have its own accepted command; every invocation must end on a complete
  stdout line; and no invocation may write a single stderr byte. The
  end-of-input acknowledgement is required rather than merely permitted: the
  acceptance contract ends the surviving invocation's input, so its accounting
  must show exactly one end of input for the restarted invocation and none for
  the terminated one, and a recording that omits it cannot pass. The accounting
  also correlates responses with commands: the trace retains each data
  acknowledgement's event identifier and the event that carried each response
  line's first byte, so a response recorded before the command it answers is a
  violation even though the ordered lines and the aggregate counts are unchanged.
  The same evidence anchors the fault witnesses: `controlled_outage` and
  `bounded_recovery` require the witness's acknowledgement to follow the
  activation or restoration, so a response whose bytes were already present before
  the transition cannot count once its newline arrives. The witness arithmetic is
  lazy, so a witness that precedes its transition fails the property instead of
  underflowing, and the accepted input offset is compared through a checked sum,
  so a positive byte count can no longer repeat a saturated offset and pass.
* *Process evidence.* The first cleanup barrier must reap at least two processes
  (the terminated primary and the escaped descendant) and the escaped-descendant
  line must precede the termination request, with termination, exit, and cleanup
  ordered by event identifier.
* *Restart recovery bound.* `bounded_recovery` now requires the restarted
  invocation to answer its first command within the scenario's liveness bound, so
  the first invocation's responses can no longer satisfy the property.
* *Strict response matching.* The driver requires each invocation's *next*
  complete line to equal the expected line, and an already-observed failure takes
  precedence over a matching line: it stops as soon as the invocation writes to
  stderr or its current stdout line exceeds the response bound, because the
  pinned fixture writes to stderr only when it is failing and a line over the
  bound can never be valid. The same health test gates every process command and
  the end-of-input step, so a failure observed by the pre-command drain stops the
  drive as well, and the wait for an exit consults the same test before its first
  blocking receive, so a failing tail folded by the acknowledgement it awaited
  ends the wait instead of becoming a receive error. The over-bound condition is
  sticky for the invocation: a line that completes with a newline still fails the
  health test, so a known-invalid response cannot become a timeout merely because
  its terminator arrived. The exit wait also ends on any complete stdout line the
  driver did not consume and on a pending byte: every expected response is
  complete and consumed by then, so a further line or even one byte can only be a
  response the checker must reject. A wrong
  response, a reported application error, or an over-long unfinished line
  therefore fails the property through the checker instead of blocking until the
  VM deadline.
* *Schedule-free passive replay.* A replayed guest reproduces the recorded
  execution, including the input it received, so the host sends nothing. Passive
  replay therefore consumes the recorded event stream in order, requires every
  event to match byte for byte, requires the stream to end with the agent-stopped
  acknowledgement, and lets the checker recompute the report from those events.
  It no longer re-decides the command schedule from its own queue timing, so a
  recording whose failing response became visible one command later than it would
  in a faster replay still replays to the same failing report.
* *Outage bookkeeping.* The driver tracks the administrative outage and restores
  the network before an early shutdown, because the agent refuses to stop while
  an outage is active. A network acknowledgement also folds the lifecycle events
  of a stopped invocation, because the runtime serializes an exit and its cleanup
  barrier as separate frames that can arrive after the host has already read the
  exit record. The fake guest enforces both the refusal and a separately
  delivered barrier, so forgetting either is a test failure rather than a
  production-only infrastructure error.
* *Process-command safety.* The driver waits for an invocation's startup line
  before its first command, folds every already-queued event before each process
  command, and treats a terminal event observed while awaiting a response as an
  orderly end. Passive replay can deliver events ahead of the commands that own
  them, so a drain parks those events and preserves the exact read order.
* *Envelope and acknowledgement correlation.* Every event's command identifier is
  bounded by the last issued command, synchronous acknowledgements must name the
  awaited command, every network acknowledgement must carry the values the host
  configured rather than only its variant, `input-accepted` contents are
  validated against the sent bytes, the shutdown drain accepts only workload
  events and requires the agent-stopped acknowledgement to name its command, and
  only passive replay may park an event whose command has not been issued yet.
* *Preparation-time bounds.* `payload_bytes` is constrained to the fixture's
  hex-encoded token limit (63 bytes) and the serialized start command, start
  event, and widest input frames are preflighted in both record and replay, so an
  undeliverable launch identity or input fails before QEMU starts. Every
  published artifact is hashed through the same bounded reader the replay path
  uses, so the recorded event stream, assertion report, workload lock, run
  manifest, replay log, and diagnostic logs are each required to fit their
  reader's limit before anything is published.
* *Acceptance harness.* The missing-raw case asserts the intended diagnostic
  instead of any nonzero exit, and a removed closure-referenced raw object is
  covered too. The fresh-root witness check concatenates each invocation's stdout
  frames before it splits them into lines, exactly as the host checker
  reconstructs the streams, so a line split across frames still counts. Only the
  acceptance report, process status, and shareable failure bundles are uploaded
  from the Phase 3 diagnostics artifact.
* *Stronger fresh-root witness.* The fixture mutates its own executable's mode in
  the immutable workload root, outside the writable overlay, and each invocation
  must report `state value=fresh root=fresh`. A reused workload root is therefore
  observable even if the overlay alone were recreated.

=== Deliberate limits

The host checker understands the checked-in acceptance fixture's line protocol
only; general protocol adapters and automatic property inference remain excluded,
as the RFD requires. The dynamically linked fixture packages the glibc
interpreter and `libc.so.6` from the pinned development environment, which is
what makes its closure reproducible in this repository; standalone dynamic
binaries remain unsupported. The workload store is shared by the runs in one runs
directory and refuses a second, different raw closure, so each source form uses
its own runs directory. The chunked command write is a host-side transport
change: the wire format, the guest's per-byte acknowledgement, and the versioned
protocol are unchanged.

The workload driver folds every already-queued event before it issues a process
command, and it treats a terminal event observed while awaiting a response as an
orderly end, so an invocation that has already exited is reported as an
application failure rather than raced. The residual window is the interval
between that drain and the guest reading the command: if the invocation is
released inside it, the guest answers with the exit record and the protocol
classifies the acknowledgement mismatch as an infrastructure error. Closing that
window completely would require a typed rejection event for a command that races
a process exit, which is a protocol change and is left to a later increment.

== Phase 4 acceptance and evidence

Phase 4 turns the Phase 1 to Phase 3 behaviour into checked-in acceptance
evidence and closes the last open RFD acceptance criterion: canonical metadata
and layer semantics must be observed correctly inside the workload root, not only
in the host staging tree.

=== Acceptance automation

`.github/workflows/ci.yml` runs, on GitHub-hosted x86-64 Ubuntu without a
container daemon:

* `scripts/rfd3-phase4-acceptance.sh`, which runs the Phase 3
  record-and-two-replay demonstration for the standalone binary, the converging
  static OCI layout, and the dynamically linked OCI layout, then adds the Phase 4
  measurements and checks;
* `scripts/rfd3-phase4-checks-test.sh`, which regression-tests the shared
  evidence checks against leaked, malformed, and unreadable artifacts; and
* `scripts/rfd3-phase4-runtime.sh`, which runs the guest-visible conformance
  suite as PID 1 in a private PID namespace. The test binary is built
  unprivileged, and only that namespace run uses the runner's passwordless
  `sudo`.

Both commands are unprivileged in the sense the RFD requires: no registry,
container daemon, host mount, TAP device, or KVM is used, and the only elevated
operation is the chroot, setuid, and mknod the guest runtime itself performs.
`scripts/rfd3-phase4-acceptance.sh` records the conformance result when it is
already root and otherwise names the checked-in runtime command, so a self-hosted
runner can run one command or the other.

=== Guest-visible OCI conformance

`crates/simferret/tests/rfd3_phase4.rs` builds one local `linux/amd64` OCI layout
with a base and an upper layer. Each layer mechanism owns its own subtree,
because opacity hides every lower child of its directory: the upper layer
legally replaces `replace/keep`, whiteouts `hide/removed` while `hide/kept`
survives, marks `opaque` opaque so its lower children disappear while the
same-layer `opaque/added` survives, and adds a symbolic link; the base layer
carries a non-default directory mode, owner, and timestamp.
`each_layer_mechanism_is_independently_load_bearing` assembles a baseline and
three variants that each omit exactly one mechanism, and requires the
lower-layer entry that mechanism should have affected to reappear with its own
bytes, mode, owner, and timestamp, so no mechanism can be masked by another.

`template_encoding_preserves_oci_conformance_metadata` decodes the encoded CPIO
template and pins every header, so a whiteout or opaque marker can never appear
in the guest image. `canonical_metadata_survives_cpio_encoding_and_is_visible_in_the_guest`
then extracts that template exactly as the guest initramfs does, materializes it
through the real runtime, and runs the pinned static BusyBox workload as the
normalized nonzero user. The workload reports what it sees inside its root:

[source,text]
----
root 755 0 0 0
bin 755 0 0 0
busybox 755 0 0 0
replace 751 2000 2000 1700000003
keep 640 1001 1001 1700000008 upper
kept 644 1200 1200 1700000005 safe
added 644 1300 1300 1700000006 added
link replace/keep
linkmode 777 1700000004
removed=absent
lower=absent
nested=absent
----

Every value matches the canonical view, so modes, owners, modification times,
symbolic links, legal replacement, whiteout, and opacity survive CPIO encoding
and are observed inside the workload root. The guest-visible check needs root to
change root and drop credentials, and a private PID namespace for the
guest-wide cleanup barrier, so it returns early without root; the unprivileged
`the_conformance_workload_can_read_every_path_it_reports` test decides the same
permissions the runtime grants the workload, and fails on a fixture the guest
run could not read. The guest-visible check is the checked-in
`scripts/rfd3-phase4-runtime.sh` command and the CI job runs it.

=== Ambient input and artifact classification

`ambient_host_environment_never_enters_the_assembled_workload` asserts the launch
environment is exactly the specification's and then assembles the same
specification in a child process that carries a distinctive canary variable,
requiring neither the canary's name nor its value to reach any retained byte.
`an_unrelated_host_file_never_enters_the_assembled_workload` places an unrelated
file beside the binary source and inside an OCI layout directory, assembles each
form twice, and requires both assemblies to agree on the closure, canonical
tree, and template identities, on every retained raw-object digest, and on the
absence of the unrelated path and content.
`a_host_source_path_never_enters_the_retained_closure` walks the whole store,
including the derived cache entry's lock, tree, and encoded template, and
requires the host source path to stay out of every retained byte.

The unprivileged acceptance run repeats the ambient check with a distinctive
canary value and requires the ambient canary value and the host output path to
stay out of the raw closure and derived lock, while the recorded launch
environment is exactly `["MODE=acceptance"]`. It also requires the run
directory, the guest image cache, the workload store, and every host-written run
artifact to be owner-only, and it records its own canary workload so the
classification check has a launch value and per-run stream tokens that cannot
occur in a shareable artifact by coincidence. Every failure bundle the Phase 3
demonstration and the canary recording published — including the ones a
tampered copy of a run directory published, and the canary recording's own
bundle, which must be among them — must carry exactly the published report and
diagnostics fields and optional sanitized log tails, and must contain none of
those canaries in plain text or in the hex encoding the event stream uses. The
check rejects an unreadable, linked, or special entry instead of skipping it, so
it never certifies a tree it did not read. The checks themselves are
fail-closed and regression-tested by `scripts/rfd3-phase4-checks-test.sh`, which
rejects a leaked canary in either encoding, an unexpected file or nested field,
a missing or untyped report, an unreadable bundle directory, a recording
without stdout, and a failed measurement producer. The run-level
`private_run_artifacts_are_owner_only_and_failures_exclude_workload_data` unit
test remains the focused regression.

=== Supported profiles, self-hosted requirements, and invocations

The supported inputs are the RFD's bounded set: a standalone fixed-address,
little-endian x86-64 Linux ELF, or one direct `linux/amd64` manifest selected by
digest from a local OCI image layout with plain or gzip layers and OCI whiteout
and opaque-directory semantics. Relocated (static PIE) binaries, standalone
dynamic binaries, device nodes, sockets, FIFOs, setuid and setgid modes, hard
links, sparse files, ACLs, unsupported extended attributes, descriptor URLs, and
embedded descriptor data are rejected before QEMU starts. No registry, container
daemon, host mount, or network access participates. `README.md` carries the same
profile statement and the exact invocations.

The unprivileged acceptance command needs x86-64 Linux, the pinned Nix
environment (QEMU, kernel, the static and dynamic C compilers, `readelf`,
`python3`, `jq`), and no elevated privilege. The guest-visible conformance
command additionally needs root for the guest runtime's chroot, setuid, and
mknod, plus a PID namespace for the guest-wide cleanup barrier. GitHub-hosted
Ubuntu provides passwordless `sudo`; a self-hosted runner needs the same or an
equivalent unprivileged path.

=== Next RFD decision

The RFD's follow-up decision is to choose between checkpoint branching,
OCI-profile expansion, and serial control optimization. The Phase 3 and Phase 4
evidence point to checkpoint branching:

* Assembly and replay are reliable across three source forms and two replays per
  form, with byte-identical normalized events and matching semantic outcome
  digests, so the packaging boundary is stable enough to build on.
* The packaged workload is small (144 KB store, 2.2 MB initramfs for the static
  forms) and records in about 10 to 20 seconds, so checkpoint size and restore
  cost can be measured on a representative filesystem and process rather than the
  built-in fixture.
* No OCI compatibility failure was observed in the accepted profile; the
  bounded layer semantics were sufficient for the static and dynamic fixtures,
  so profile expansion has no concrete mismatch to justify it.
* Record and replay cost is dominated by the QEMU run itself, not the serial
  control protocol; the chunked writer already removed the one observed
  transport bottleneck, so control optimization has no measured target.

The next increment should therefore measure checkpoint-tree size, restore cost,
and branching throughput on this packaged workload. OCI-profile expansion and
serial control optimization move earlier only if checkpoint evidence shows they
block it.

=== Deliberate limits

The guest-visible conformance workload is the pinned static BusyBox and reports
metadata through its own `stat`, `readlink`, and existence tests; it is a
repository fixture, not a general OCI conformance suite. The check extracts the
encoded template exactly as the guest initramfs does and runs the real runtime,
but it is a host-run guest test rather than a full QEMU boot, so it does not
re-verify the kernel's own initramfs extraction beyond the Phase 3 acceptance
boots. The identity and adversarial coverage map names the checked-in tests
rather than generating one test per case, so a future change that removes a test
must also update this evidence.
